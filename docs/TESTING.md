# Testing

The system has many seams: analogue hardware, flash, a radio protocol, a phone
OS, the internet, a database. Each seam gets its own test tier, and the tiers
are arranged so that almost everything runs on a laptop with no hardware.

The model is borrowed from projects that live with the same seams:

| Idea                                   | Where it comes from                | Here                                    |
|----------------------------------------|------------------------------------|-----------------------------------------|
| Pure units tested on the host          | Linux kunit                        | Unity native env, Jest, `go test`       |
| Firmware core runs on the host         | Zephyr `native_sim`                | `lib/telemetry-core`, simulator env     |
| Conformance vectors shared by all impls| Android CTS, protocol interop suites| `schema/vectors/`                       |
| Behavioural tests against a real system| Linux kselftest                    | integration tests with fakes and Postgres|
| Hardware in the loop, off the PR path  | KernelCI, LKFT                     | `scripts/hil/` nightly smoke            |

## Tiers

### Tier 0: static

Type checks, linters, `go vet`, warnings as errors in the native firmware
build. Runs on every push.

### Tier 1: unit tests on the host

Rule: **anything that does not touch a peripheral compiles and tests on the
host.**

| Area     | Runner                          | Command                          |
|----------|---------------------------------|----------------------------------|
| firmware | PlatformIO Unity, `native` env  | `make -C sensor test`            |
| app      | Jest via `jest-expo`            | `npm test --prefix app`          |
| api      | `go test`                       | `make -C api test`               |

Firmware tests live in `sensor/test/test_<subject>/`. Each directory is one
Unity binary. The `native` environment compiles `lib/telemetry-core` and any
`sensor/src` files listed in its `build_src_filter`; it never compiles
`sensor/src/platform/`.

### Tier 2: conformance vectors

`schema/vectors/*.json` hold encoded bytes and their decoded fields for every
wire format, plus invalid inputs and the error they must produce. They are
generated by `schema/tools/gen_vectors.py` and committed. CI regenerates them
and fails if the committed files differ.

Every codec implementation (C++, TypeScript, Go) has a test that loads the
vectors and checks:

- decode(hex) equals the decoded fields,
- encode(decoded) equals the hex byte for byte,
- each invalid vector produces the named error.

This is the tier that prevents schema drift between components. Adding a
field means adding a vector first.

### Tier 3: integration with fakes

Whole subsystems run together on the host with fake peripherals.

- **Firmware:** `SyncSession` + `RingStore` on a memory block device + a
  `FakeTransport`. Scenarios: full pull from an empty cursor, resume after
  disconnect mid-chunk, ack frees slots, ring wraps and reports drops, set-time
  back-fills.
- **App:** `CollectionService` + `FakeTransport` + `MemoryRepository`;
  `UploadService` + `FakeApiClient`. Scenarios: first and repeat visits, a wiped
  phone, the secured ack reaching the sensor, gaps from corrupt slots, dropped
  chunks, link loss, rejected records, retry after a 5xx, and the full
  collect, upload, revisit loop. `FakeSensor` itself is tested against the
  same behaviours as the firmware's `SyncSession`.
- **API:** handlers with `httptest` against a real Postgres started by
  testcontainers or by `docker compose`. Scenarios: idempotent re-post of a
  batch, partial overlap, malformed record, ack ranges.

### Tier 4: the simulator

A PlatformIO environment builds `lib/telemetry-core` for the host and links it
to a TCP transport. The app has a matching dev-only `TcpTransport`. The app
then exercises the real protocol implementation with no board. This is the
same trick as Zephyr's native simulation board and is the highest-leverage
test asset in the repo: one protocol implementation, tested from the real
client.

### Tier 5: end to end

`make e2e` starts Postgres and the API with `docker compose`, starts the
simulator with a seeded ring of records, runs the app's sync services headless
in Node against the simulator and the API, and asserts:

1. every seeded record lands in Postgres exactly once,
2. the API returns the full ack range,
3. the ack propagates back into the simulator's ring and frees the slots,
4. re-running the sync produces zero new rows.

This single scenario is the "pipeline works" gate. It runs nightly and on
demand, not on every push.

### Tier 6: hardware in the loop

`scripts/hil/serial_capture.py` resets the attached board and captures its
serial output for a fixed window with timestamps, refusing to attach if another
process holds the port. `scripts/hil/ble_probe.py` is the reference BLE
central: it scans for the service UUID, decodes the advertisement, connects,
opens a session, sets the time, pulls records with CRC and seq checks, and
acknowledges. Both are building blocks; `scripts/hil/smoke.py` will chain
them and assert. Manual or nightly.

macOS only lets a process use Bluetooth after the user grants it in a system
prompt, so run `ble_probe.py` from your own terminal the first time; a
sandboxed or non-interactive shell hangs waiting for CoreBluetooth to power on.

Power measurements are recorded by hand in `docs/power.md` with the firmware
version and `PowerPolicy` values used; they are not automated.

## Test data and fakes

- Fakes live next to the interface they fake: `sensor/test/fakes/`,
  `app/src/transport/fake.ts`, `api/internal/store/memstore.go`.
- Fakes are deterministic. A fake clock is advanced explicitly; a fake
  transport delivers bytes when told to.
- Seeded records for the simulator and the e2e run come from
  `schema/vectors/`, so the e2e test also exercises the vectors.

## CI layout

Each scope has its own workflow file under `.github/workflows/` with a path
filter, so a firmware change does not run the app job:

| Job        | Triggers on changes under          | Runs                                        |
|------------|------------------------------------|---------------------------------------------|
| `schema`   | `schema/`                          | regenerate vectors, `git diff --exit-code`  |
| `firmware` | `sensor/`, `gateway/`, `lib/`, `schema/` | `pio test -e native`, `pio run` per firmware |
| `api`      | `api/`, `schema/`                  | `go vet`, `go test` with a Postgres service |
| `app`      | `app/`, `schema/`                  | `tsc --noEmit`, lint, Jest                  |
| `e2e`      | nightly schedule, manual           | `make e2e`                                  |

Every job must pass before merge. The gateway compiles in the `firmware` job
but has no tests yet.

## What to write when you add something

| You added…                    | Write…                                                    |
|-------------------------------|-----------------------------------------------------------|
| a field to a wire format      | a vector first, then make all three codecs pass           |
| a core subsystem in firmware  | a Unity test dir with a fake for anything it depends on   |
| a HAL implementation          | nothing automated; add a check to the HIL smoke           |
| a sync behaviour in the app   | a Jest test against `FakeTransport`                       |
| an API endpoint               | an `httptest` test and, if it writes, a Postgres test     |
| a bug fix                     | the failing test first, in the lowest tier that shows it  |
